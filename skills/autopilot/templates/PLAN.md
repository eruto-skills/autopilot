## Tasks

Each task has:

- `id` — short stable string
- `priority` — integer, lower = earlier
- `passes` — `false` initially, `true` once the acceptance test runs green
- `description` — what needs to be done in 1 sentence
- `acceptance` — **user-observable** check (a command that exits 0, a manual browser interaction, a curl response, a file diff). Not "code looks clean", not "DDD layered".
- `notes` — running notes the agent appends across iterations; trimmed at the start of each iteration to the most recent 5 lines

### Acceptance criteria — concrete vs abstract

The single most important discipline. → [completion-criteria](../references/completion-criteria.md)

- ❌ `acceptance: "the auth module is well-structured"`
- ❌ `acceptance: "tests pass"` (which tests? what do they prove?)
- ✅ `acceptance: "npm run test:e2e tests/auth/login.spec.ts exits 0, and screenshot tmp/login-success.png shows the dashboard"`
- ✅ `acceptance: "curl -s localhost:3000/api/rules returns a JSON array, and DELETE /api/rules/1 followed by GET /api/rules returns one fewer item"`

### Example

```yaml
- id: T01
  priority: 1
  passes: false
  description: Wire up the /rules CRUD endpoints to the real Postgres table
  acceptance: |
    psql -c "TRUNCATE rules" &&
    curl -X POST localhost:3000/api/rules -d '{"name":"r1"}' | jq '.id' &&
    curl -s localhost:3000/api/rules | jq 'length' returns 1 &&
    curl -X DELETE localhost:3000/api/rules/1 &&
    curl -s localhost:3000/api/rules | jq 'length' returns 0
  notes: []

- id: T02
  priority: 2
  passes: false
  description: Render the /rules page so it lists, creates, edits, and deletes rules
  acceptance: |
    `npm run test:e2e tests/rules.spec.ts` exits 0 (covers list/create/edit/delete flows)
    AND screenshot tmp/rules-list.png shows at least one rule in the table after creation
  notes: []
```
